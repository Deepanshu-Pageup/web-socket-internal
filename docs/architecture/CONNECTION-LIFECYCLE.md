# Connection Lifecycle

**Status:** Draft — revised for the independent architecture (ADR-0004); not re-reviewed or approved
**Related:** [System architecture](SYSTEM-ARCHITECTURE.md) ·
[Channel and event flow](CHANNEL-AND-EVENT-FLOW.md)

> Protocol-level message names, error codes, close codes, and timings are
> **not finalized**. They are **[DESIGN]** items owned by this project
> (ADR-0018) and must be specified and approved before implementation. Nothing
> here defines final protocol behavior.

## 1. States

```text
 [Upgrading] -> [Established] -> [Closing] -> [Closed]
      |               |
      +-> [Rejected]  +-> [Terminated] (heartbeat failure, limit breach, slow client)
```

| State | Meaning |
|---|---|
| Upgrading | HTTP upgrade received; validation in progress |
| Rejected | Upgrade refused before a WebSocket exists |
| Established | Connection ID assigned, connection registered, connection-established message sent |
| Closing | Client or server initiated close; cleanup running |
| Terminated | Server closed the connection due to a fault or policy |
| Closed | Fully unregistered; no state remains |

## 2. Connect

1. The SDK obtains a short-lived connection token from the consuming backend
   (ADR-0020), then connects to the project's configured endpoint, declaring a
   protocol version **[DESIGN]**.
2. Transport performs explicit upgrade handling and validates: token (integrity,
   expiry, deployment), origin policy, protocol version supported, server not
   shutting down. Where the token is carried **[DESIGN]**; avoid locations that
   are routinely logged.
3. On failure: reject, or accept then send a protocol error and close
   **[DESIGN]**. Never reveal secrets or configuration.
4. On success: accept the socket, the connection manager assigns a connection ID,
   registers the connection with its validated claims, and the protocol layer
   sends the connection-established message.
5. The client may then subscribe (see
   [CHANNEL-AND-EVENT-FLOW.md](CHANNEL-AND-EVENT-FLOW.md)).

Connection IDs must be unique within the deployment and generated by the server
with a cryptographically secure source; they must not be client-chosen.
Format **[DESIGN]**.

## 3. Heartbeat and liveness

- The server detects dead connections through WebSocket-level ping/pong and/or
  an application-level heartbeat defined by the protocol **[DESIGN: which is
  required]**.
- A connection that misses the heartbeat deadline is terminated and cleaned up.
- The SDK implements the client side of the heartbeat.
- Intervals and timeouts are configuration values with validated bounds.
  Defaults **[OPEN]**.

## 4. Token expiry during a connection

Whether an established connection is closed, re-authenticated in place, or
allowed to continue after its token expires is a **[DESIGN]** item (ADR-0020).

## 5. Limits enforced during the lifetime

- Maximum inbound message size; oversize frames close the connection.
- Maximum subscriptions per connection and inbound message rate **[OPEN values]**.
- Bounded outbound buffer per connection; a slow client that exceeds it is
  terminated rather than allowed to grow memory unbounded.
- Invalid or malformed protocol messages produce a protocol error and, if
  repeated or severe, termination.

## 6. Disconnect and cleanup

On any close (normal, error, timeout, termination):

1. Connection manager unregisters the connection.
2. Channel manager removes all of its local subscriptions and deletes empty
   channel records.
3. Presence membership is updated if presence is enabled (a member is removed
   only when the user has no remaining connection in that channel).
4. Timers and buffers for the connection are released.

Cleanup must be idempotent: duplicate close/error events must not throw or
double-remove state.

## 7. Reconnect

The server keeps no session across connections. A reconnecting client (the SDK,
using backoff) receives a new connection ID, obtains a fresh token and any needed
private-channel authorization, and resubscribes. Events published while
disconnected are not replayed. Backoff parameters and server hints, if any,
are **[DESIGN]**.

## 8. Graceful shutdown

1. Stop accepting new upgrades and mark readiness as not ready.
2. Notify or close existing connections with an appropriate close code
   **[DESIGN: code and expected SDK reconnect behavior]**.
3. Wait up to a configured deadline for pending writes, then force-close.
4. Clear in-memory state and exit; no stale local state is left behind.
